# Q&A 模式规则

> 用途：core 在对话中已有完整报告，或用户附带报告文件时，不重跑流程，进入答疑
> 适用范围：不限于技术追问，包括任何人生问题

---

## 第一步：失效检查（每次续问先做）

```
python shared/scripts/check_freshness.py --dir <工作目录>
```

按输出分别处理（正本 `shared/versioning.md` §2），「需更新」项先处理再答：

| 输出 | 处理 |
|---|---|
| chart_id 不同（出生数据或计算设置变了，含校时） | 旧分析、旧 core_summary 标「待更新」，不得直接引用；在新盘上重做初始推导，或明确告诉用户"这是旧盘结论，待更新" |
| audit_id 不同 | 依赖分盘宫位 / 宫主的结论先复核再用 |
| 基准日之后运期变了 | 用今天重新定位 MD/AD/PD（PD：`calculator/scripts/dasha_query.py --file structured_data.md --date YYYY-MM-DD`）；不采信表里的"→当前 / ← 当前"标记（那是生成日快照）；按日期重定位属于日期对照，不属于手动推导 |
| 过运快照之后已有换座（即使不满 3 个月），或快照超过 90 天 | 有计算环境 → 用 `calculator/scripts/transit.py` 重取；没有 → 明确声明"过运数据已过期"，不引用旧的当前过运位置与 Sade Sati 阶段，只用 Dasha 层回答 |
| 规则版本不同 | 回答里标明哪些旧结论需要复核 |
| user_context.md 在分析之后更新过 | 更新表达与建议；新事实与结论冲突时进入反馈复核 |
| 无法判断（如 5.1 之前的报告没有版本行） | 引用旧结论时当作待复核，并在回答里说明 |

未来过运窗口只引用「未来过运换座时间表」或 `transit.py` 的结果，禁止凭记忆写换座日期。

**年龄换算**：用户以年龄叙述事件（"我22岁那年…"）时，先换算成公历年份并向用户确认（"22岁≈2019年，对吗？"）再查 Dasha 归属；对外时间表述以公历年份为主，年龄只作括号附注。

## QA 阶段背景规则（与分析阶段相反）

分析阶段（Step 1-4、Step 5、Step 6、反馈复核）对 user_context.md 的不读不写、Step 4.5 的只读不写，在 QA 阶段**解除**。权限正本：`shared/permissions.md` §4。

```
1. 回答前先读 user_context.md（如果存在）——不了解背景就回答人生问题，模板话术可能直接撞上真实伤痛。
2. 背景不改结论：user_context 影响的是"怎么说"和"补充什么"（表达方式按 UC 调整；建议结合实际处境具体化）。
   结论只在 shared/permissions.md §5 的三类情况下修改：读数错误 / 规则应用错误 / 新输入推翻旧前提，
   用 shared/scripts/analysis_record.py change 记"原结论 → 新证据 → 修改原因 → 新结论"。
   按用户反馈修正的类别写「反馈复核」，先 stage --set reviewed --read-feedback（mode 变 calibrated）。
3. 伦理检查（每次回答前过一遍）：
   □ 丧亲 → 对已故的人禁用"改善关系""多沟通"类话术，按"已经失去"写
   □ 创伤（家暴/出轨/破产/重病等）→ 相关话题禁套模板，盘面信号结合事实解读
   □ 矛盾 → 盘面方向与已知经历直接矛盾时承认矛盾，说明盘面是趋势不是命令；禁"盘面如此"搪塞；
     矛盾属于偏差反馈，按下方处理规则 6 分诊
4. 增量回写：用户在 QA 中新补充的传记信息（关切/经历/事件/特质），按 reader 模块「增量回写规则」
   追加到 user_context.md 对应小节，写完回读确认；只写增量、不改分析结论。
   寒暄、澄清追问、情绪表达、对分析结论的评价（"准""不准"）不是传记事实，不写。
```

## 处理规则

1. **时机类问题**：用户问"什么时候找到工作/对象/买房？"
   → 查 Dasha 时间线 + 对应宫位（10宫/7宫/4宫）；SAV 仅极端值(>32/<20)时作强度佐证、不定时机方向
   → 窗口分辨率正本 `shared/time_window.md` §1：MD 只给背景趋势；事件性窗口至少落到 MD×AD；
     问到月份、季度内先后或窄于完整 AD 的窗口 → 先用 `dasha_query.py` 读原生 PD 再给月级候选；
     PD 缺失或未通过检查时只给 AD 阶段窗口，并说明分辨率不足
   → 大运、小运各自按 house_framework 五档定档，叠加按 `shared/time_window.md` §6：
     两层都属正/负照四组合读法；任一层混合或平淡 → 分层陈述，不给统一评级
   → 节点当值按 p1_p12 P7.4 节点专用条件判定
   → 档位必须与 appendix.md 的 Dasha 速查表一致；速查表未覆盖的时段按 house_framework 现算并注明
   → L7/UL/Venus 当值 ≠ 结婚、Ketu/8宫 ≠ 分离（p1_p12「三轴分离」）
   → 给具体时间窗口，不说"总有一天"

2. **方向类问题**：用户问"适合做什么行业/学什么/去哪个城市？"
   → 引用10宫+AmK+格局（行业） / 4/5宫（学业） / 4/9/12宫（方位）
   → 给具体建议

3. **运势类问题**：用户问"今年/明年运势怎么样？"
   → 用今天重新定位当前 MD/AD → 各自管哪些宫 → 按 MD×AD 两层叙述（shared/time_window.md §6）
   → 按领域分述（事业/财运/感情/健康）
   → 问到具体月份：先在本模块用 dasha_query.py --month 读 PD 回答（受 check_chart 能力范围限制：PD 不启用时只到 AD 阶段）；
     需要行运日期、年盘或多系统交叉时再引导 timing 模块（普通"今年运势"走 Mode B + A；明确要年盘才走 Mode C）

4. **技术追问**：用户问"8宫怎么理解""Moon为什么弱"
   → 引用报告中的 P1-P12 数据 + 宫位诊断，展开解释

5. **化解类问题**：用户问"怎么改善/怎么补救？"
   → 基于弱点宫位给行动建议（不推荐宝石/仪式等迷信手段），写法按 shared/grounding_basic.md
   → 方向：利用强星赛道、避开弱星领域、时机选择

6. **偏差反馈**：用户说"不像我""分析不准"
   → 按 shared/error_correction.md §1 分诊：数据问题 / 规则应用问题 / 解释形态问题 / 时间问题，分别处理
   → 不一律转向"出生时间可能不准"：时间来源可靠时，先怀疑规则在这张盘上的适配；
     只有时间来源不可靠，或多条时间敏感结论（上升、分盘）同时偏、盘在换座点附近时，才建议说"校准时间"运行 rectifier
   → 修改结论走变更日志；无法解决的写「未解决」，说明缺什么证据
   → 不追加新预测去弥补，不承诺"做完完整分析会更准"，不因用户情绪调整档位

## Q&A 约束

- **深度由问题决定**：
  - 简短追问（一个数据点、一个概念、一句确认）→ 直接在聊天里答：结论 + 正反要点 + 依据出处
  - 需要完整推导的判断性 / 时机问题，或用户要文件 → 写入 `qa_<主题>.md`（如 `qa_job_timing.md`），聊天框只简报 1-2 句结论 + 文件路径
- **正反双审（最重要）**：回答任何判断性问题，同时列出支持和制约的数据，不准只挑一边。文件化回答用下方模板；聊天里的简短回答保留"支持 / 制约 / 结论"三项即可。

  ```markdown
  ## Q：[用户原始问题]

  ### ⚖️ 正反双审

  **支持 [X] 的数据：**
  - [数据点] → [含义]
  （按实际数量列；没有就写"未发现"）

  **制约 [X] 的数据：**
  - [数据点] → [含义]
  （按实际数量列；没有就写"未发现"）

  ### 🎯 综合判断

  [基于以上正反数据的结论，3-5 句话]
  [必须指出"哪些条件下偏向支持""哪些条件下偏向制约"]
  [禁止简单地"取平均"——必须给出条件性结论]

  ### 📍 时间维度（问题涉及时机时）

  [MD 背景 → AD 阶段 → PD 月级候选 / PD 未读或缺失（写明实际分辨率）]
  [带括号推导依据，两层分开写：（XXXX-XXXX 年 Saturn 大运：L10=Saturn，正面 X 条/负面 Y 条→X 档；
   其中 Saturn-Mercury 小运：正面 X 条/负面 Y 条→Y 档；叠加读法按 shared/time_window.md §6）]

  ### 🔗 分盘交叉（问题涉及 4/5/7/10 宫主题时）

  [按下方"分盘交叉规则"执行]

  ### 💡 行动建议

  [基于综合判断给出具体可操作的建议，按实际需要写，通常 2-3 条]
  ```

  **禁止行为**：
  - 用户想听好话 → 只列支持数据 → ❌ 卖乐观
  - 用户有焦虑 → 只列制约数据 → ❌ 卖悲观
  - 忽略 BAV/SAV/Shadbala 中与用户预期矛盾的数据点 → ❌ 选择性引用
  - 为了两边对称硬凑条目 → ❌ 某一侧确实没有就写"未发现"
  - 在"综合判断"段简单地"取平均"或"折衷"→ ❌ 必须给条件性结论

- **基于数据**：所有回答引用 structured_data 和已有报告，不编造
- **引用原文**：关键结论附上报告原文出处（如"p4第290行"），方便用户对照
- **区分层次**：结构层（有没有这个信号）和执行层（做起来顺不顺）分开讲，不混为一谈
- **语言风格**：70%大白话 + 20%数据 + 10%注释
- **跨领域**：问题属于 career/love 深度领域时，引导用户跑对应模块获得更详细分析

## 分盘交叉规则（判断性问题适用）

**回答判断性问题时交叉检查相关分盘。**

交叉前按 `shared/divisional.md` §1 读「分盘可信度声明」：相关分盘 `⚠️ 边界敏感` → 由分盘 Lagna 派生的落宫/宫主结论降为候选场景，并说明哪一类结论会随边界侧改变；旧数据无审计 → 标"输入稳定性未验证"，不把"直接计算成功"或出生证来源当成分盘稳定。引用分盘宫主时按 `shared/divisional.md` §2 分线A（分盘内部宫主，读「分盘内部宫主表 + 尊贵度」）与线B（本命宫主职落分盘宫）标注，禁裸写"D10 10宫主"。

```
步骤1: 定位问题涉及的核心宫位
  例：留学 → 9宫(远方)+4宫(家)+12宫(海外)
  例：找工作 → 10宫(事业)+6宫(日常工作)
  例：结婚 → 7宫(婚姻)+2宫(家庭)

步骤2: 回读structured_data.md的分盘部分（不能只看报告摘要）
  检查对应分盘中同一宫位/行星的信号：
  - 4宫问题 → D4（财产/居住）
  - 5宫问题 → D5（权力/创造力）
  - 7宫问题 → D9（婚姻/灵魂品质）
  - 10宫问题 → D10（事业/成就）
  - 综合问题 → 检查所有已启用分盘

步骤3: 分盘信号与D1对比
  D1和分盘一致 → 信号增强，直接确认
  D1和分盘不同 → 必须说明修正方向
    例："D1的Moon在4宫=强回家信号，但D4的Moon在10宫=
         物质层面锚点是事业不是地点。分盘修正了D1的结论。"

步骤4: 分盘可用性执行
  分盘标注为 ❌（时间精度不足）→ 不得引用，明确说明"因时间精度限制无法分析"
  分盘标注为 ⚠️（含"边界敏感"）→ 分盘星座层可引用；落宫/宫主层只写候选场景或条件句
  分盘标注为 ✅ → 正常引用
```

⚠️ 问题涉及 4/5/7/10 宫且对应分盘已启用时，不能只用 D1 回答就收工：D1 只是表面层，分盘提供灵魂层(D9)和物质层(D4)的修正。
