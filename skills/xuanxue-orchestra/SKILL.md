# xuanxue-orchestra —— 问题驱动的调度、交叉与档案协议

## 一、定位与优先级

- 实践层只管流程与档案；方法与判词权威在四门（bazi-core、liuyao-core、ziwei-core、vedic），章节名以各自 SKILL.md 为准。
- **用户只陈述问题**：跑哪几门、几门并行、要不要回问由 §三 自定，用一句话调度说明交代；不要求先选体系、不弹菜单；用户点名体系或已给盘时从其点名与盘。
- 冲突时四门优先；起课先加载本技能，再用 `skill` 加载对应门；没加载门 skill 不得排盘断卦。
- 不做：不排盘、不装卦、不断吉凶、不替用户摇卦、不心算干支、不手排紫微、不合成新技法、不做梅花体用。
- 四门共同边界：不断死期、不诊断病名、不给投资标的与仓位、不说「必成必散」、不过门槛断第三者/离婚/官非；合盘只走紫微「合盘」或吠陀 synastry；健康与财务只给方向并提示专业人士。

## 二、起课契约：参数卡

起课台两种入口：①固定门传参数卡（出生字段与 case.json 的 `birth` 同名，另有 `system`/`systems`/`focus`）；②自动模式传问题与已知信息（`system:"auto"`、`expect` 取 `conclusion`/`discussion`），门由 §三 定。两者都原样存 `params.card`，自动模式按 `expect` 走 §4.5 的结论或讨论：

```json
{"system":"auto","question":"我 30 岁以后该不该转行？","expect":"conclusion","label":"陈某","calendar":"gregorian","date":"1990-06-15","time":"08:30","uncertaintyMinutes":0,"sex":"male","place":"上海","lng":121.47,"tz":"Asia/Shanghai","timeSource":"birth-certificate","declaredMinutes":5,"focus":["career"]}
```

（固定门入口则 `system` 取 `bazi`/`liuyao`/`ziwei`/`vedic`，字段同上并按该门补齐；未给的字段一律缺省，不补默认。）

| 门 | 必填 | 口径与边界 |
|---|---|---|
| bazi | date（公历/农历+闰月）、time、出生地或 lng、tz | sex 不给两顺逆都列；无时间→时柱暂缺只留受影响分支；边界→列候选 |
| ziwei | date、time 或 shichen、**sex 必须给**、出生地（海外 --lng+--tz） | 收公历/农历；时辰跨界列候选盘；大陆 1986–1991 问夏令时 |
| vedic | **只收公历** date、出生地→经纬度+IANA tz、timeSource | time 无则 --date-only；无时间→上升/宫位/分盘/Dasha 未计算 |
| liuyao | 问事+谁测、起卦时间（公历含时区或四值干支）、阴阳动静（lines 或卦名+动爻） | 不替用户摇卦；一事一断；干支跑脚本；截图不清或卦名矛盾先停 |

`focus` 只用 career/wealth/marriage/family/health/timing/study；`timeSource` 只用五值；六爻卡字段名直接用。**最多问三项并说明为什么；默认值写进参数卡；不编造、不补默认；原始与计算时间分开记。**

## 三、问题驱动调度

### 3.0 先分两轴：算命（命）与卜卦（卜）

两件事，输入不同、不能混：

| | 算命（命） | 卜卦（卜） |
|---|---|---|
| 输入 | 固定的出生时刻 + 出生地（本命盘） | 问事这一刻 + 起卦方式（摇卦 / 字背 / 数字 / 时间）或吠陀提问盘（提问时刻 + 提问地） |
| 对象 | 这个人一生的结构与时间表 | 这一件事的成败与应期 |
| 能做 | 格局、倾向、六亲、长期趋势、应期窗口、合盘、择日 | 一事一断：成败、指向、应期候选 |
| 本技能里 | 八字、紫微、吠陀本命（D1 + 分盘）；行运 / 年盘属于应期校验 | 六爻；吠陀 Prashna（提问盘，v5.3 起收录） |

四条硬规则：

1. **算命不用六爻**：六爻不批本命（`liuyao-core` 明写），也不替用户摇卦；本命问题只走八字 / 紫微 / 吠陀。
2. **卜卦不借命门下断**：具体事件走卜卦——有摇卦走六爻；没有摇卦但能确定提问时刻与地点，可走吠陀 Prashna；两者都没有就说明「这次没有卜」，命门只给「背景趋势与窗口」并注明「这不是卜卦结论」。反过来卜卦结论不能反推本命结构。
3. **两套卜卦是两个传统，不混判**：`vedic` v5.3 起收录 prashna 模块——用提问时刻与提问地起独立提问盘，不需要生辰，**不读本命盘、不读写本命产物，也不做验前事**（模块自带隔离，cross-natal 失败关闭）。六爻与 prashna 各自独立成盘、独立判定，**不互相「确认」、不互相改判、不折算概率**；用户点名哪套就走哪套，没点名就按数据条件选一套并说明理由。
4. **应期与择日是第三类**：命门的应期（八字大运流年、紫微大限流年、吠陀 Dasha）属于算命；紫微流日挑日子属于择日；六爻与 prashna 的应期属于「这一次问事的应期」。三类不互相替代。

### 3.1 问题分诊（先抽后问）

从原话抽六要素，抽不出的才问（并入一次回问，≤3 项）：**对象**（本人/他人/一事）、**类型**（本命/事件/应期/合盘/健康/选择/失物出行/学业/天气）、**时间**（过去/当下/未来窗口）、**数据**（生辰精度、有无摇卦）、**交付**（结论/讨论）、**边界**（重断/健康/财务，触到降强度）。

### 3.2 法门证据矩阵

| 门 | 能给什么证据 | 数据前提 | 时间粒度 |
|---|---|---|---|
| bazi | 格局、做功、层级、六亲、应期 | 生辰（无时辰可降） | 年/大运/流年，可到月 |
| ziwei | 宫星四化、大限流年流月流日、合盘 | 生辰+时辰+**性别** | 年→月→日，宫位细节 |
| vedic | Dasha/行运/分盘、synastry、专项 | 公历生辰+地点（时间可缺） | 多年 Dasha 级，可到 PD 月/日 |
| prashna（vedic 模块） | 一事成不成、某人会不会动、大致何时、双方在靠近还是走远 | **提问时刻（秒级）+ 提问地（经纬度/时区）**，无需生辰 | 事件级；时间副层给粗略窗口 |
| liuyao | 具体事成败、应期候选、来意 | 用户自摇的卦+起卦时间 | 一次性事件，应期到日/月 |

**没有生辰→八字/紫微/吠陀本命不可用（给盘除外）；没有摇卦→六爻不可用；时间精度差→八字时柱分支、紫微候选盘、吠陀宫位与 Dasha 降级，六爻只受起卦时间影响**。prashna 不受生辰限制，但要能确定**提问时刻与提问地**。

命证据（命门：结构 / 倾向 / 窗口）与卜证据（六爻 / prashna：这一次的成败 / 应期）性质不同，交叉时只做「窗口 vs 事件」互证（§七），不互相冒充。

### 3.3 最少充分集（默认不铺开四门）

```
1 筛数据：按 3.2 划掉不可用门并记原因。
2 定主证：按类型定 1 门；交叉门只在「能对同题同窗给独立证据且能区分分支/改建议」时加，至多 2 门。
3 封顶：默认 1 门；2–3 门是例外；4 门只在点名或重断复核时用。
```

| 问题类型 | 主证门 | 可交叉 |
|---|---|---|
| 本命、性格、六亲 | 八字 | 紫微宫位、吠陀 Dasha |
| 具体事件、失物、出行、天气 | 六爻（有摇卦）/ prashna（无摇卦但能定提问时刻与地点，或用户点名吠陀卜卦） | 命门同窗趋势（§七）；六爻与 prashna 不同时互证 |
| 应期、某年某事、挑日子（无卦） | 八字大运流年或紫微流日流月 | 吠陀 Dasha、紫微流年 |
| 关系合盘 | 紫微合盘或吠陀 synastry | 都可用就各跑再对照 |
| 健康倾向、选择决策 | 八字 P8；有卦加六爻 | 紫微疾厄（只给方向）；看两选项期限 |

- **值得交叉**：两门方法独立、各有依据，问题能被独立覆盖，且会改置信或改建议；**浪费**：显全面、同源同法、一门不覆盖、只要方向判断。都写进 `cross.plan`。

### 3.4 数据不足时的退路

- **无生辰**：先给能给的——六爻（引导用户自己摇卦，明确「我不替你摇」）、吠陀 prashna 提问盘（只需提问时刻与地点，不需要生辰；一次一个具体问题），或问最少信息（生日/时段/地点），或只做资料解释；不硬凑命门。
- **只有日期无时间**：八字时柱暂缺只留不受影响分支；紫微列 2–3 个候选时辰盘请用户拿已知事实对照；吠陀 date-only，上升/宫位/分盘/Dasha 写「未计算」。
- **无卦只有事**：六爻不参与，命门给窗口趋势并注明「无事件级证据」；用户接受且有提问时刻与地点时，可改用 prashna 起提问盘（要说明这是吠陀卜卦，不是六爻）。
- **红线**：缺数据就明说缺什么，**不编出生时间、不替摇卦、不用 A 门结论补 B 门参数**。

### 3.5 调度与并行

- **顺序**：单门；或前一门结论决定后一门是否值得跑。
- **并行**：2–3 门互不依赖时用 `subagent`，每路只负责一门，任务自包含（参数卡、问题、时间窗、输出格式）、互不引用结论、只回证据、**都不写档案**；汇总与落档在主会话。
- **派发要点**：只给该门 SKILL.md、参数卡、问题原话与时间窗；只回 `{门, 结论[], 依据[], 标签原话, 应期候选[], 覆盖/未覆盖, 数据缺口}`，不总结、不跨门推断、不自行补参数。
- **不并行**：需要一门结论定下一门、要先确认数据、脚本不可用、用户要边聊边推进时。

## 四、交叉拟合协议

### 4.1 信号归一

每门输出压成同一形状：`{主题, 时间窗, 方向: 支持/反对/无关/未覆盖, 依据一句话, 本门标签原话}`。**不换算概率、不跨门比较标签**；同门多条同向证据合并；**「未覆盖」≠「反对」**——没看这个题就是没看。

### 4.2 三角验证（同一问题、同一时间窗）

| 情形 | 标记 | 处理 |
|---|---|---|
| ≥2 门各自有依据地支持 | **多门共同支持** | 写 `cross.agree`；都实、无未解决反证→`strong`，一门较弱→`medium` |
| 1 门支持、其余未覆盖 | **单门支持** | 注明哪门，不给多门标签、不加权 |
| 1 门支持、1 门反对 | **冲突** | 两读并列+分辨条件+可观察预测，写 `cross.conflicts`，不按票数裁 |
| 全部未覆盖 | **无交叉证据** | 照单门交付，明说这次没有交叉 |

### 4.3 信息可能性展开

列 2–4 个可能解释/分支（如事业：体制内/专业路线/创业），每支写：含义、哪门支持（可空）、权重（高/中/低，不是概率）、**什么信息或时间点能区分它**；给「当前最可能」与依据。

### 4.4 缺口清单

缺什么（生日、时辰、摇卦、某段经历、某时间点事件）、能区分什么、成本（零成本/一句话/摇卦）。**一次最多问 3 项，能先给部分就先给**；写进 `cross.gaps`。

### 4.5 讨论 vs 结论

- **讨论**：给分支与权重、邀请补事实、说清哪条信息会改判，不硬给结论。
- **结论**：结论先行+证据矩阵+置信标签+应期；冲突照样并列。
- 混合（多数）：先给能给的结论，再补「哪条事实能改判」。

### 4.6 禁止

①拿 A 体系结论当 B 体系依据；②为「显得全面」硬凑四门；③把两门一致说成概率翻倍；④把未覆盖说成反对；⑤用多数票裁冲突；⑥把子代理的总结当证据；⑦用同一门第二条线索冒充第二门。

## 五、单门流水线

1. 建参数卡；缺项只问会改变本次结论的。
2. `skill` 加载对应门，按入口表选模式。
3. 跑脚本：按各门 SKILL.md 运行配置；八字/六爻先设 `$env:PYTHONUTF8="1"`、`$env:PYTHONIOENCODING="utf-8"`；紫微 tsx 报 `spawn EPERM` 改 `node "$env:USERPROFILE\.cache\ziwei-core\prebuilt\run\pan.cjs"`；吠陀用 `vedic-calc-env` 解释器跑 `build_chart.py` 再 `check_chart.py`。
4. 读盘按门骨架；本技能不解读。
5. 结论挂证据：每条写 `text/evidence/system/tag/verification/window`，说不出不写。
6. 落档（§九），应期写 `timing[]`/`nextCheck` 并告知到点复盘。

检查点：参数卡齐、候选已标；脚本自检过；结论有证据与验证状态；JSON 过校验。失败就报错原文，不手排兜底。

## 六、多门对照

同一命主多门并跑：同一 `subject.birth` 派生各门参数，每门独立跑完自己的协议，**严禁拿 A 体系结论当 B 体系依据**；只在同一问题、同一时间窗对照并合档。汇总表一行一主题：

| 主题 | 八字（依据+标签） | 紫微（派别+标签） | 吠陀（信号→模式） | 六爻（卦理+标签） | 归一方向 | 处理 |
|---|---|---|---|---|---|---|

一致只作各自加强，不换算概率；冲突两读并列写条件与观察点（§四）。

## 七、问事与命门互证

卜卦（事件级：六爻或 prashna）与命门（八字/紫微/吠陀本命，趋势级）只在**同一问题、同一时间窗**上互证：各自先独立跑完再对照，不对照不同问题。六爻与 prashna 是两套传统：**各自独立成盘、各自判**，不同时用来「互证」，也不拿一套的结论去改另一套；同题两套都跑时按「两个子问题各有答案」并列，各标各的标签。

- 三个维度：方向（成/不成 vs 有结构/无结构）、时间窗（重叠/先后/错位）、强度（六爻高/中/低或 prashna 内部档；命门本门标签）。
- 判定：卜卦成 + 命门同窗有同类结构 → 互证（按 §四 标 `strong`/`medium`）；卜卦成 + 命门无结构 → **单门支持**，命门记「未覆盖」不是反对；卜卦不成 + 命门有结构 → 冲突，写「窗口有结构但此事未成」的分辨条件；时间错位 → 两窗口都列出，写哪个先到、怎么观察。
- 禁止：拿卦象/提问盘解释命盘、拿命盘改卜卦、拿命门裁卜卦成败、拿卜卦否命门趋势；六爻不批本命；prashna 不读本命盘、不做验前事（`prashna` 模块自带隔离，cross-natal 失败关闭）。缺卜卦时命门单给窗口趋势并注明「无事件级证据」。

## 八、报告骨架（对用户的回复）

固定六段，档位只改篇幅：

1. **调度说明**（一句：选了哪几门、为什么、没选的门为什么不用）。
2. **结论先行**（每条带本门标签与验证状态，先答所问）。
3. **交叉拟合**（共同支持/单门支持/冲突与分辨；无交叉证据就明说）。
4. **可能性分支**（讨论模式必写）。
5. **还缺什么/下一步**（≤3 项，能先做先做）。
6. **档案 id + 应期提醒**（nextCheck / 要不要设提醒）。

简明=1+2+6 各一句；标准=六段齐；详细=再加证据矩阵与分支表。不复述参数卡、不写套话、不把冲突藏进「综合来看」。

## 九、落档协议

- 库在工作区根 `xuanxue-cases\`：`index.json` + `<id>\case.json` + `<id>\readings\YYYY-MM-DD-<system>.md` + 可选 `<id>\chart\`。
- id：`YYYY-MM-DD-<subject>-<门或multi>-<focus>`；新建＝新命主/新摇卦/新问题，更新＝追问、补门、复盘；六爻一事一卦独立 case，本命多门同一问题合档。
- `index.json` 同步对应行（updatedAt/status/verification/confidence/summary/nextCheck），从 case.json 派生、冲突以 case.json 为准回写，按 updatedAt 降序。
- 只追加不覆盖 `conclusions`/`timing`/`verificationLog`/`readings`，修订写新条目并注 v2。
- 读档追问：核对 birth、口径、技能版本，变了只重算受影响部分并加 reading；旧结论不作废，引用注版本。
- 字段、枚举、校验按 `references/case-format.md`；时间用带时区 ISO 8601。
- **卜卦 case（六爻或 prashna）**：`subject.birth` 记的是**起卦 / 提问时刻与地点**，不是命主出生；`params.notes` 写明「起卦盘」或「prashna 提问盘，不读本命」；`charts` 放该盘关键值（六爻放本卦/变卦；prashna 放内部档、时间副层、Tajika 方向），`systems` 仍是 `liuyao` / `vedic`。prashna 的产物目录是 `prashna_<时间戳>_<label>/`，与工作目录里可能有形态不同的问答（`prashna_meta.json`、`structured_prashna.md`）。

**多门 case 必须写 `cross` 块**（单门可省略；`systems` ≥2 时必填，`systems`/`cross` 里的门必须等于实际跑过的门）：

```json
{"cross": {"plan": "一句话：为什么选这几门、为什么不需要其他门", "agree": [{"statement": "多门共同支持的结论", "systems": ["bazi", "ziwei"], "strength": "strong"}], "conflicts": [{"topic": "分歧主题", "readings": [{"system": "bazi", "text": "..."}, {"system": "vedic", "text": "..."}], "condition": "分辨条件/可观察预测"}], "gaps": [{"missing": "缺什么信息", "why": "能区分什么"}]}}
```

约束：`agree[].strength` 只用 `strong`/`medium`；`agree[].systems` ≥2 且 ⊆ `systems`；`conflicts[].readings` ≥2、`system` ⊆ `systems`、`condition` 非空；`gaps` ≤3；不用处省略键，不写 `null`。`cross` 不替代 `conclusions`（agree 要有对应门结论支撑）；可随新证据修订（刷新 `updatedAt` 并在 notes 记一句），历史判定进 `verificationLog`。

## 十、复盘与验证闭环

- 盲测纪律：先落档再告知；`readings[].at`、`createdAt` 不得回填改写；看过经历只记 fitted，不得称盲测。
- 四档：untested 无事实；fitted 只算解释一致；blind-checked 推导时未接触答案、先落档、后由外部结果核对；forward-checked 预测先固定、到期按事前标准判定。只升不降，改版后旧成绩不套用。
- 到点：`nextCheck <= 今天` 逐档问结果，写回 `verificationLog`（`{at,item,result,note}`）与 `timing[].status`（hit/miss/partial），同步 index 行并刷新 updatedAt。
- 复核 `cross`：agree 是否仍成立、condition 是否已可判（判了写 `verificationLog`）；补上的 gaps 记录；冲突被裁定时不许改写成一致。
- 无法判定：不写 hit/miss，留 pending 并把原因写进 `params.notes`；不得事后放宽窗口。

## 十一、体检协议

- 时机：技能迭代后、依赖变更后、排盘可疑、用户点名。命令：`pwsh -NoProfile -File <本技能目录>\scripts\health-check.ps1`（技能加载时会给出本技能目录的绝对路径，装在哪都一样），默认写当前工作区的 `xuanxue-skills\health.json`；`-Quick`/`-Full` 可选；脚本未就位就报告。
- 读结果：`checkedAt`、`skills.<门>.status`（ok/warn/fail）、`detail`、`error`、`notes`；有 fail 退出码 1，warn 不算失败；失败项贴原文，无 fail 才可用。
- 解释器与入口按「环境变量 → 玄学运行时 → 本机已有环境」解析，结果写在 `notes` 里；缺环境先跑同目录 `scripts/setup-runtime.ps1`（一条命令建好 venv 与紫微入口），再按插件 `docs/SETUP.zh.md` 排环境问题。
- 失败：紫微 EPERM→预编译入口（缺入口先跑 `scripts/build-ziwei-prebuilt.ps1`）；八字/六爻缺依赖→报告缺什么，不静默安装；吠陀缺环境→`calculator\scripts\check_env.py`。
- 不建 case；既有 case 须重排时追加检查记录并更新 updatedAt，结论不自动改。

## 十二、技能迭代协议

1. 先读对应 SKILL.md 与 references，定位章节，按「必须/建议/可选」分级。
2. 草案写 `xuanxue-skills\drafts\<技能名>\`：改后完整文件 + `CHANGE.md`（问题、改法、验证、回滚）。
3. 确认后落回插件源码仓库的 `skills\<技能名>`（GitHub 安装后这份在 profile 的 `node_modules\dsh-xuanxue\skills`，直接改会被下次更新覆盖，要改就改仓库并发版）；若这台机器另有同源副本（例如 `~/.agents\skills\<技能名>`）按用户指定改那一份。
4. **禁止**草案写进 `.agents\skills` 或 `.dsh\skills`；禁止未确认改生效副本。
5. 落地后跑自检+体检，CHANGE.md 记「已落地+目标+日期」。
